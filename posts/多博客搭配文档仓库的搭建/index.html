多博客搭配文档仓库的搭建

这是一篇介绍搭建多博客仓库和文档仓库的文档，实现更新文档仓库通过GitHub Actions工作流，将文档更新内容推送到多个博客仓库中，各博客仓库在触发自动构建然后网站更新

思路介绍

问题来源: 原来搭建jekyll搭配Chirpy主题后，在里面_posts文件夹下编写文档然后推送发布到仓库，仓库Actions自动编译构建发布Github Pages，这没问题
突发奇想，我如果想在github pages搭建多个不同的博客系统喃，比如再用hexo搭建一套，而文档还是那些文档，不可能在把文档复制一份到hexo项目的source/_posts文件下吧，每次编写一篇文档我都要复制一次，那就太麻烦了，所以有了文档和项目分离的想法。 那如何去做喃，根据搜索了解，思路大致那么几个：

  1. 专门一个文档仓库blog-posts(用来管理文档)，每次编写修改这个文档仓库并推送，github actions向另外的博客仓库发送信号，另外的博客仓库来拉取跟新内容重新构建
  2. blog-posts仓库更新，github actions直接推送_posts文件下内容到博客仓库对应位置，博客仓库actions触发更新重新构建
  3. 将blog-posts仓库设置成博客仓库的子模块，blog-posts更新后，博客仓库重新拉取子模块push触发actions重新构建。

原本打算实现思路1的，但是又突然想到想把博客仓库设置成私有的，不想让别人可以直接访问仓库获取文档源文件，捣鼓半天发现Github免费版账号，想要使用Github Pages必须吧这个账号设置成public的，原本的前两个思路就不是那么适用了，有点麻烦还不好实现，最终还是选择思路3把blog-posts设置成博客仓库的子模块可能要好些。

💡思路1的实现

这种思路是一种CI/CD自动化中的一个标准模式
核心思路是：将文章仓库blog-posts作为一个“触发器”，每次推送更新时，自动向两个博客仓库(jekyll-blog,hexo-blog)发送“远程唤醒信号”
这个远程唤醒方式主要有两种：respository_dispatch和workflow_dispatch

🗝️ 准备工作：必需的密钥 (Personal Access Token)

这两种自动化方案之所以能工作，核心在于一个经过授权的令牌(Personal Access Token, PAT), 它允许一个仓库去唤醒另一个仓库的工作流。

  1. 创建PAT：登录GitHub，在Settings -> Developer settings -> Personal access tokens -> Tokens(classic) -> Generate new token(classic)
  2. 配置权限：在”Select scopes”部分，务必勾选repo区域(这会授予对私有仓库的完全控制权)
  3. 生成并保存：点击生成后，立刻复制并保存生成的token值，它只会显示一次
  4. 添加到Secrets：回到准备做”唤醒”动作的仓库(即blog-posts)，进入Settings -> Secrets and variables -> Actions -> New repository secret,将刚复制好的PAT黏贴进去

👑 方案 A：使用 repository_dispatch (推荐)

这是官方推荐的，文章仓库扮演”消息发布者”, 博客仓库扮演”监听者”，一有新文章就自动构建

  1. 在博客仓库中创建监听器 在每个博客仓库(jekyll-blog和hexo-blog)的.github/workflows/目录下，创建一个YAML配置文件(例如deploy-on-update.yml)
    这个监听工作流的重点，是让它响应on: repository_dispatch事件

    点击展开详细的YAML文件内容 
    
 # .github/workflows/deploy-on-update.yml (在 jekyll-blog 和 hexo-blog 仓库中各放一份)  
 name: Deploy on Blog Update

 # 监听 repository_dispatch 事件，并且只关心 event-type 为 'blog-updated' 的信号  
 on:  
   repository_dispatch:  
     types: [blog-updated]  

 jobs:  
   build-and-deploy:  
     runs-on: ubuntu-latest  
     steps:  
       - name: Checkout 仓库代码  
         uses: actions/checkout@v4  
         with:  
           submodules: 'recursive'  # 务必加上，这样才能拉取最新的文章子模块  

       - name: 设置 Node.js (用于 Hexo)  
         uses: actions/setup-node@v4  
         with:  
           node-version: '18'  
     
       - name: 安装依赖 (如果是 Jekyll 则需要 Ruby 环境)  
         # 这里假设你的博客根目录有 package.json  
         run: npm install  

       - name: 构建博客  
         run: npm run build # 或者你对应的构建命令，如 jekyll build  

       - name: 部署到 GitHub Pages  
         uses: peaceiris/actions-gh-pages@v3  
         with:  
           github_token: $  
           publish_dir: ./public # 根据你的博客生成目录调整

  2. 在文章仓库中创建触发器
    在文章仓库blog-posts的.github/workflows/目录下，创建一个触发器工作流(例如tigger-blogs.yml)。它的任务很简单：当文章更新时，通知博客仓库。

    点击展开详细的YAML文件内容 
    
 # .github/workflows/trigger-blogs.yml (在 my-blog-posts 仓库中)
 name: Trigger Blog Builds

 # 当文章被推送到 main 分支时触发
 on:
   push:
     branches: [ "main" ]
     paths: # 优化：仅当文章目录下有变化时才触发
       - '_posts/**'
       - '**.md'

 jobs:
   trigger-builds:
     runs-on: ubuntu-latest
     steps:
       # 使用官方 action 来发送 repository_dispatch 信号
       - name: 触发 Jekyll 博客构建
         uses: peter-evans/repository-dispatch@v3
         with:
           token: $ # 关键！使用 PAT
           repository: your-username/jekyll-blog # 你的 Jekyll 博客仓库
           event-type: blog-updated           # 与监听器中定义的 type 一致
           client-payload: '{"ref": "$", "sha": "$"}' # 可选，传递更多信息

       - name: 触发 Hexo 博客构建
         uses: peter-evans/repository-dispatch@v3
         with:
           token: $
           repository: your-username/hexo-blog
           event-type: blog-updated
           client-payload: '{"ref": "$", "sha": "$"}'[reference:0]

🔑 方案 B：使用 workflow_dispatch

这种方式更直接，文章仓库的工作流直接调用API，唤醒博客仓库中特定的工作流。

博客仓库的工作流(保持不变)
确保你的博客仓库中一个可被workflow_dispatch触发的工作流：

点击展开详细的YAML文件内容 

```yaml
# .github/workflows/deploy.yml (在 jekyll-blog 和 hexo-blog 中)
name: Deploy Blog
on:
  workflow_dispatch: # 允许被远程触发
  # ... 其他如 push 等触发条件
jobs:
  build-and-deploy:
    # ... 构建和部署步骤，与方案一类似 ...
```

文章仓库的触发器
在文章仓库的触发器工作流中，使用curl或actions/github-script来调用GitHub API。

点击展开详细的YAML文件内容 

```yaml
# .github/workflows/trigger-blogs.yml (在 my-blog-posts 中)
name: Trigger Blog Builds via workflow_dispatch
on:
  push:
    branches: [ "main" ]
    paths:
      - '_posts/**'

jobs:
  trigger-builds:
    runs-on: ubuntu-latest
    steps:
      - name: 触发 Jekyll 博客工作流
        run: |
          curl -X POST \
            -H "Accept: application/vnd.github+json" \
            -H "Authorization: token $" \
            https://api.github.com/repos/your-username/jekyll-blog/actions/workflows/deploy.yml/dispatches \
            -d '{"ref":"main"}'[reference:1]
```

👣 完整工作流

设置完成后，只需要执行日常的git commit -m "add new post"和git push到blog-posts仓库。接下来的整个流程会自动完成，就像有一个隐形的流水线在工作：

  1. git push文章到blog-posts
  2. GitHub检测到blog-posts的push事件，触发其trigger-blogs.yml工作流。
  3. 工作流运行，使用PAT_TOKEN向jekyll-blog和hexo-blog发送信号。
  4. 两个博客仓库收到信号，立即启动它们各自的deploy-on-update.yml工作流，拉取blog-posts的内容。
  5. 工作流拉取自己最新的仓库代码、安装依赖、构建静态网站，并最终部署到GitHub Pages。
  6. 整个流程自动完成，这样两个博客站点都更新了。

💡思路2的实际实现

这个思路是我最先操作并成功了的，blog-posts和jekyll-site两个仓库，文档仓库更新后触发工作流推送同步到jekyll-site仓库的_posts文件中，使用git推送的触发博客仓库的工作流，博客仓库重新构建博客并发布GitHub Pages
仓库设置:

  1. blog-posts仓库是私有的，它需要拉取jekyll-site仓库并推送，所以需要配置PAT，以便于推送更新内容到博客仓库
  2. jekyll-site仓库必须是公开的，才能使用GitHub Pages，需要在仓库Settings -> Pages -> Build and deployment -> Source下选择GitHub Actions
  • 在blog-posts仓库中.github/workflows/文件夹下创建工作流文件sync.yml
点击展开详细的YAML文件内容 

name: Sync Blog Posts

on:
  push:
    branches: [main]
    paths: ['_posts/**']   # 只在 posts 内容更新时触发

jobs:
  sync:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout blog-posts
        uses: actions/checkout@v6
        with:
          path: blog-posts

      # 同步到 Jekyll 仓库
      - name: Sync to Jekyll site
        # uses: dmnemec/copy_file_to_another_repo_action@main
        env:
          GH_TOKEN: $
        run: |
          git clone --depth 1 --branch main https://x-access-token:${GH_TOKEN}@github.com/zhoulinhu/jekyll-site.git jekyll-site
          rm -rf jekyll-site/_posts/*.md
          cp -R blog-posts/_posts/* jekyll-site/_posts/ 2>/dev/null || echo "No files to copy"
          cd jekyll-site
          git config user.name "sync-bot"
          git config user.email "bot@example.com"
          git add _posts
          git diff --cached --quiet || git commit -m "Sync posts from blog-posts" || echo "No changes to commit"
          git push origin main

  • 在jekyll-site仓库中的.github/workflows/文件夹下创建工作流文件pages-deploy.yml
点击展开详细的YAML文件内容 

name: "Build and Deploy"
on:
  push:
    branches:
      - main
      - master
    paths-ignore:
      - .gitignore
      - README.md
      - LICENSE

  # Allows you to run this workflow manually from the Actions tab
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

# Allow one concurrent deployment
concurrency:
  group: "pages"
  cancel-in-progress: true

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v6
        with:
          fetch-depth: 0
          # submodules: true
          # If using the 'assets' git submodule from Chirpy Starter, uncomment above
          # (See: https://github.com/cotes2020/chirpy-starter/tree/main/assets)

      - name: Setup Pages
        id: pages
        uses: actions/configure-pages@v5


      - name: Setup Ruby
        uses: ruby/setup-ruby@v1
        with:
          ruby-version: 3.4
          bundler-cache: true


      - name: Build site
        run: bundle exec jekyll b -d "_site$"
        env:
          JEKYLL_ENV: "production"

      - name: Test site
        run: |
          bundle exec htmlproofer _site \
            \-\-disable-external \
            \-\-ignore-urls "/^http:\/\/127.0.0.1/,/^http:\/\/0.0.0.0/,/^http:\/\/localhost/"

      - name: Upload site artifact
        uses: actions/upload-pages-artifact@v4
        with:
          path: "_site$"

  deploy:
    environment:
      name: github-pages
      url: $
    runs-on: ubuntu-latest
    needs: build
    steps:
      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4
